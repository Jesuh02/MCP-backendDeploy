## Plan: Arquitectura Hexagonal — Backend como Gateway Único

### TL;DR

Actualmente la app Android realiza **~200+ operaciones directas** contra Supabase (PostgREST) y **~10 operaciones** contra Cloudflare R2 (AWS Signature V4), exponiendo credenciales sensibles (`SUPABASE_ANON_KEY`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`) en el cliente móvil. El plan es migrar **todo** al backend Node.js usando **arquitectura hexagonal (puertos y adaptadores)** con Clean Architecture, SOLID y responsabilidad única. La app Android solo hablará con el backend vía REST + JWT. Las subidas a R2 usarán **URLs prefirmadas** generadas por el backend. La migración será **por fases** (dominio por dominio).

### Pasos de Implementación (por Fases)

#### **FASE 0: Fundamentos (transversal)**

1. Crear `shared/errors/` con clases `AppError`, `NotFoundError`, `ValidationError`, `UnauthorizedError`, `ForbiddenError` — cada error con `statusCode`, `message`, `isOperational`
2. Crear `shared/Result.js` — patrón Result monádico: `Result.ok(value)` / `Result.fail(error)`
3. Crear `shared/pagination.js` — helper estándar `{ data, total, page, pageSize, totalPages }`
4. Crear `config/container.js` — DI container simple (factory functions que inyectan adaptadores en use cases)
5. Crear `infrastructure/auth/JWTAdapter.js` — `sign(payload)`, `verify(token)`, `decode(token)` usando `jsonwebtoken` + `bcryptjs`
6. Crear `infrastructure/middleware/AuthMiddleware.js` — middleware Express que verifica JWT en `Authorization: Bearer <token>`, inyecta `req.user = { userId, username, roles }`, rechaza con 401 si inválido. Excepciones para rutas públicas (`/health`, `/api/v1/auth/login`, `/api/v1/auth/register`)
7. Refactorizar index.js — extraer configuración de Express a `config/server.js`, dejar index.js solo como punto de entrada que llama `container.js` → `server.js` → `app.listen()`

#### **FASE 1: Dominio Auth + Users (primera migración)**

Crear puerto de salida `domain/ports/out/IUserRepository.js` — interfaz con métodos: `findById(id)`, `findByUsername(username)`, `findByEmail(email)`, `create(user)`, `update(id, data)`, `exists(username)`, `findWithRoles(username)`, `assignRole(userId, roleId)`, `getUserRoles(userId)`, `searchByUsername(query, limit)`, `findByIds(ids[])`

### Cambios en Android (por cada fase)

Para **cada fase**, el trabajo en Android consiste en:

1. **Crear/ampliar interface Retrofit** en `network/` — por ejemplo `CourseApi.kt` con todos los endpoints de la fase
2. **Crear RemoteDataSource** en `data/remote/` — wrapper que llama a la API Retrofit, maneja errores HTTP, mapea JSON a entidades Room
3. **Refactorizar repositorios** en `data/repository/` — reemplazar llamadas directas a `SupabaseClient`/`SupabaseRepository` por llamadas al `RemoteDataSource`
4. **Eliminar código directo** de `SupabaseClient.kt`, `SupabaseRepository.kt`, `SyncRepository.kt` para la entidad migrada
5. **Agregar interceptor JWT** — `OkHttp Interceptor` que añade `Authorization: Bearer <token>` a cada request al backend

- **Compatibilidad**: las rutas legacy siguen funcionando durante toda la migración (Android viejo + Android nuevo coexisten)

### Decisiones

- **JWT sobre API Key**: elegido JWT por ser estándar, permite roles embebidos en el token, refresh token flow
- **Presigned URLs sobre proxy upload**: elegido para no duplicar ancho de banda especialmente para videos grandes (+100MB)
- **Migración por fases sobre reemplazo total**: reduce riesgo, permite validar fase por fase, Android puede tener código dual temporalmente
- **API versionada (`/api/v1/`)**: permite evolucionar sin romper clientes existentes; las rutas legacy coexisten en `/`
- **DI Container simple (factory functions)** sobre framework DI (awilix/inversify): menos overhead, suficiente para el tamaño del proyecto
- **Supabase PostgREST** como adapter (no raw SQL): aprovecha el cliente `@supabase/supabase-js` que ya tiene, evita inyección SQL presente en courseRoutes.js
