 1. VISIÓN GENERAL
═══════════════════════════════════════

La app Android realiza ~200+ operaciones directas contra Supabase (PostgREST)
y ~10 operaciones contra Cloudflare R2 (AWS Signature V4), exponiendo
credenciales sensibles en el cliente móvil. Este backend Node.js implementa
Arquitectura Hexagonal pura (Ports & Adapters) con Clean Architecture,
principios SOLID estrictos, y seguridad multi-capa. La app Android solo se
comunica con el backend vía REST + JWT.

El sistema gestiona 24 dominios funcionales, cada uno siguiendo el patrón:
  Puerto (interfaz) → Servicio de dominio (caso de uso) → Adaptador (infra)

Stack tecnológico:
  - Runtime:       Node.js + Express (ESM modules)
  - Base de datos: Supabase (PostgreSQL via PostgREST)
  - Storage:       Cloudflare R2 (S3-compatible, presigned URLs)
  - Auth:          JWT (bcryptjs), RBAC
  - AI/LLM:        DeepSeek / OpenRouter / qwen embedding
  - TTS:           OpenAI Text-to-Speech API
  - Video:         FFmpeg (análisis + compresión)
  - RAG:           pgvector embeddings + búsqueda semántica
  - Notifications: FCM (push) + Resend (email)
  - Payments:      Wompi gateway
  - Deploy:        Railway + Docker


═══════════════════════════════════════
 2. PRINCIPIOS ARQUITECTÓNICOS
═══════════════════════════════════════

1. Dependency Inversion (SOLID-D)
   El dominio NUNCA depende de infraestructura. Los puertos (interfaces)
   viven en el dominio; los adaptadores en infraestructura. La inyección
   se realiza en el Composition Root (container.js).

2. Single Responsibility (SOLID-S)
   Cada clase/módulo tiene UNA razón para cambiar.
   Ejemplo: SupabaseUserRepository solo persiste usuarios.

3. Open/Closed (SOLID-O)
   Agregar un nuevo dominio = agregar entidad + puerto + adaptador +
   servicio + controlador + rutas. Sin modificar lo existente.

4. Liskov Substitution (SOLID-L)
   Todo adaptador puede sustituirse por otro que implemente el mismo
   puerto sin romper el sistema.

5. Interface Segregation (SOLID-I)
   Puertos granulares. No interfaces monolíticas. Cada puerto define solo
   las operaciones que su consumidor necesita.

═══════════════════════════════════════
 4. PATRÓN DE COMPOSICIÓN (DI CONTAINER)
═══════════════════════════════════════

Archivo: src/config/container.js

Flujo de wiring:
  1. Instanciar adaptadores de infraestructura (JWTAdapter, R2Storage, etc.)
  2. Instanciar adaptadores nuevos (OpenAITTSAdapter, FFmpegVideo, LLM, RAG, GitHub, Cache)
  3. Instanciar repositorios Supabase (inyectando client)
  4. Instanciar servicios de dominio (inyectando puertos via constructor)
  5. Instanciar controladores (inyectando servicios)
  6. Retornar mapa { controllers, services, adapters }

Constructor injection pattern (destrucción de objeto):

  class XDomainService {
      constructor({ xRepository, fileStoragePort }) {
          this.repo = xRepository;
          this.storage = fileStoragePort;
      }
  }

Entrypoint de la aplicación (index.js):

  import { createApp, startServer } from './src/config/server.js';
  const { app } = createApp();
  startServer(app, PORT);

═══════════════════════════════════════
 7. SEGURIDAD MULTI-CAPA
═══════════════════════════════════════

7.1 AUTENTICACIÓN
 - JWT Bearer Token obligatorio en /api/v1/* (excepto /auth, /health, /mcp)
 - Access Token: 24h, payload: { userId, username, roles }
 - Refresh Token: 7d
 - bcryptjs (10 salt rounds) para passwords
 - Middleware authMiddleware.js verifica en cada request

7.2 AUTORIZACIÓN (RBAC)
 - Rol 1: Estudiante
 - Rol 2: Docente / Creador
 - Rol 3: Admin
 - Middleware requireRoles(...) para rutas sensibles
 - Ownership verification: solo creator modifica sus recursos

7.3 SEGURIDAD HTTP
 - Helmet.js: CSP, HSTS, X-Frame-Options, X-Content-Type-Options
 - CORS configurable por entorno (origins whitelist)
 - Rate Limiting:
   - Global: 100 req/min
   - Auth: 5 req/min (login, register)
   - Upload: 10 req/min
 - Sanitización anti-XSS
 - Body limits: 50MB uploads, 1MB JSON

7.4 VALIDACIÓN
 - Joi schemas para TODA entrada (body, params, query)
 - Middleware validate(schema) centralizado
 - IDs parametrizados (PostgREST) — no SQL raw
 - ValidationError.fromJoi(error) con detalles

7.5 SECRETOS
 - NINGUNA credencial en Android
 - .env (no committed) con todas las keys
 - Presigned URLs para uploads R2 (temporales, 15min)
 - Service Account Keys en servidor únicamente

 8. PATRONES DE IMPLEMENTACIÓN

8.1 RESULT MONAD
 Archivo: src/shared/Result.js

   Result.ok(data)     → { success: true, data }
   Result.fail(error)  → { success: false, error }
   // Inmutables via Object.freeze
   // Control de flujo SIN excepciones

8.2 CONTROLADOR (arrow function properties)
   class XController {
       constructor({ xService }) {
           this.service = xService;
       }
       getById = async (req, res, next) => {
           try {
               const result = await this.service.getById(req.params.id);
               if (result.isFail()) return res.status(404).json(result.error);
               res.json(result.data);
           } catch (err) { next(err); }
       };
   }

8.3 RUTA (factory function)
   export function xRoutes({ xController }) {
       const router = Router();
       router.get('/:id', xController.getById);
       router.post('/', validate(schema), xController.create);
       return router;
   }

8.4 SERVICIO DE DOMINIO
   class XDomainService {
       constructor({ xRepository }) { this.repo = xRepository; }
       async getById(id) {
           const data = await this.repo.findById(id);
           if (!data) return Result.fail(new NotFoundError('X no encontrado'));
           return Result.ok(data);
       }
   }

  - unhandledRejection: log + exit(1)


═══════════════════════════════════════
 11. DECISIONES ARQUITECTÓNICAS
═══════════════════════════════════════

 Decisión                       │ Justificación
 JWT sobre API Key              │ Estándar, roles embebidos, refresh flow
 Presigned URLs sobre proxy     │ No duplicar bandwidth (+100MB videos)
 API versionada /api/v1/        │ Evolución sin romper clientes
 DI Container simple (factory)  │ Suficiente para el tamaño del proyecto
 Supabase PostgREST client      │ Evita SQL injection
 Input Ports como interfaces    │ Documenta contratos, facilita testing
 DataMapper en infraestructura  │ Entidades puras sin snake_case
 Result<T,E> monádico           │ Control de flujo sin excepciones
 ESM modules (.js ext)          │ Estándar moderno, tree-shaking
 Dual exports (named+default)   │ Flexibilidad de import
 Legacy wrappers                │ LLMAdapter envuelve LLMService existente
 Legacy redirects               │ Compatiblidad backward con app Android

 12. ENTIDADES DE DOMINIO — Regla de Pureza
═══════════════════════════════════════

Las entidades son clases PURAS:
  ✗ NO importan nada de infraestructura
  ✗ NO conocen Supabase, R2, JWT, Express
  ✗ NO tienen fromSupabaseRow() (eso va en DataMapper)

  ✓ SÍ usan camelCase

El mapeo snake_case ↔ camelCase se realiza en DataMapper.js
